# 后端重启后的任务状态恢复

任务编排由 practice-server 的内存线程执行，不能在 JVM 重启后续跑。
后端保持单副本并使用 `Recreate` 部署策略：先停止旧实例，再启动新实例，
避免两个实例同时编排、或新实例误清理旧实例的任务。不要将此服务扩为多副本，
也不要恢复滚动更新；多实例编排需先引入持久化任务所有权和租约。

新实例在开放 HTTP 服务前检查所有未结束任务。对于重启中断的任务：

1. 在所有已配置集群中，按精确的 `topic4.io/task-id` 标签删除对应 Job，
   等待 Job 和 Pod 全部消失。Kubernetes 无法访问或清理超时会阻止启动，
   不会提前释放数据集占用。该标签同时写入 Job 和 Pod。
2. 在同一事务内，将任务标记为“执行失败”、未结束的复制记录标记为 `FAILED`，
   并结束关联的计算调度计划及未结束的分配记录。
3. 写入 `TASK_INTERRUPTED` 事件、`SERVER_RESTART` 原因和结束时间。
   已完成、已失败、部分完成的记录保持原状。再次启动不会重复修改已结束记录。

此恢复过程不将中断任务视为成功，不自动重跑业务计算，也不删除数据集源副本。
用户可在失败记录结束后重新提交。独立的数据复制调度计划不属于计算任务恢复范围。
