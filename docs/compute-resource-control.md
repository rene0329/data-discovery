# 计算作业资源控制

## 调度规则

资源按单个数据集、单种计算模式对应的计算作业分配。一个业务任务包含多个作业时允许分批启动，对比任务的两种模式分别申请资源。

原位计算保留既有拓扑规则：优先副本所在计算节点，其次副本同站点的非中心计算节点，再按路径累计延迟升序、瓶颈带宽降序、节点编号升序选择其他非中心计算节点，最后回退到中心节点。同站点内部仍保留原候选顺序。集中式计算保持中心节点约束；外部方案保持指定目标节点和副本。

逻辑拓扑及路径搜索算法不变。资源不足会跳过该候选；所有候选暂时不足时进入等待状态。超过全部已知候选节点总容量的规格会失败并说明原因。未知资源不能视为充足。

## 分配与恢复

`task_compute_job` 持久保存作业身份、资源需求、选定副本和节点、Kubernetes Job 名称及 UID、状态和结果。业务任务与作业记录在同一事务中创建。

协调器使用 MySQL 连接级锁 `topic4-compute-scheduler` 串行协调本系统的资源分配。节点可用量依据 Kubernetes allocatable 减去未结束 Pod 的有效资源 requests；同一快照尚未计入的提交意图另外扣除。绑定完成后以 Kubernetes 申请量为准。

作业使用必需的节点亲和性限定本次选点，不直接设置 `nodeName`，由 Kubernetes 调度器做最终容量判断。提交前跳过资源不足的候选；Job 创建后若遇到其他系统作业竞争资源，保持原 Job 等待，不自动删除并重新选点，以避免绑定与删除之间的竞争误杀已开始的作业。等待超时或管理员取消时才停止作业。不承诺严格先进先出，不抢占其他任务。

等待作业不占用计算工作线程。后台周期同步已有 Job；后端重启后继续关联持久化作业。创建响应不确定时按稳定名称查询，已确认的 Job 丢失或计算失败时不自动重复执行，避免重复训练及其他副作用。取消后只有确认 Job 与 Pod 均已停止，才进入终态。终态 Job 的清理失败会继续重试。

外部方案中较慢的持久副本复制使用独立工作线程，避免阻塞其他计算作业的调度；复制和迁移保留原来的完整性检查与业务语义。第一版保留后端单副本及 Recreate 部署，不能直接扩容为多个后端副本。

## 资源与状态

计算容器和数据准备容器均显式配置 CPU、内存、临时存储 requests 与 limits。GPU 按整数设备数量申请。临时数据目录设置容量约束，调度申请量考虑输入数据大小。CPU 限制不代表独占物理 CPU，网络、磁盘和内存带宽也不具有独占保证。

业务状态包括等待资源、数据准备中、计算中、取消中及结束状态。排队、数据准备和计算分别计时。数据读取凭证使用固定 Secret `default/topic4-compute-input-tokens` 中每作业独立的键；等待期间刷新凭证，避免一小时的凭证有效期被等待耗尽。后端仅获得该 Secret 的读取及更新权限，不能创建、删除或访问其他 Secret。Job 结束并清理后移除对应键。

配置位于 `app.resource-control`：

| 环境变量 | 默认值 | 含义 |
| --- | --- | --- |
| `RESOURCE_CONTROL_POLL_INTERVAL_MS` | 3000 | 状态同步间隔 |
| `RESOURCE_CONTROL_MAX_ACTIVE_JOBS_PER_TASK` | 4 | 每个业务任务同时获准运行的作业数 |
| `RESOURCE_CONTROL_WAIT_TIMEOUT_MINUTES` | 1440 | 等待资源时间上限；0 表示不限制 |

## 接口与上线

- `GET /api/v1/tasks/{taskId}/jobs`：查询资源规格、作业状态和等待原因，不返回内部资源覆盖或结果原始 JSON。
- `POST /api/v1/tasks/{taskId}/cancel`：管理员发起异步取消，客户端继续查询直至确认终态。
- 旧任务编辑接口不能直接改写持久化计算任务状态。活动任务不能删除；清空只删除已确认终态的任务，并保留任务编号的单调增长。

上线前必须执行 `practice-server/src/main/resources/db/migration/V20261108_1__durable_compute_scheduling.sql`，并创建固定凭证 Secret 及对应的最小权限 Role、RoleBinding。本项目未自动运行这份 SQL，应先检查表是否已存在并备份数据库结构。升级前等待旧版本活动任务结束；代码通过 GitHub 和 `PUSH=1 build-topic4` 构建后，部署不可变提交 SHA 镜像。后端及前端分别验证。

当前生产核查为单 Kubernetes 集群。不要直接把多个独立集群视为一个全局资源池；跨集群的公平性、配额和故障切换需要另外验证。本次也不引入成组调度、严格公平队列或运行中迁移。
